# Поиск по описанию задачи в Code Lab

Дата: 2026-11-07  
Ветка: `audit/fixes-2026-11-06`  
Статус: первая рабочая версия подключена к полю описания задачи; автоматические сценарии проверяются. Это детерминированный поиск по словарям, правилам и библиотеке, а не свободная генерация решения языковой моделью.

## Цель

Человек описывает результат обычными словами, не зная названий HTML/CSS/JavaScript-конструкций. Лаборатория должна найти реальные элементы языка, показать их отношения и подходящие фрагменты, объяснить, почему они появились в выдаче. Результаты остаются в штатной классификации языков и разделов.

Примеры:
- кнопка, которая выполняет действие по нажатию;
- ссылка на другую страницу;
- раскрывающийся блок;
- подсветка заголовка в шапке при наведении;
- данные из двух источников с выводом в нескольких местах страницы;
- боковая панель, которую можно свернуть и снова открыть.

## Текущая архитектура

### Разные способы ввода

- **Описание задачи** — поле в `vtree.js`. Передаёт полный запрос в `GET /api/search/task` (сервер ограничивает длину 500 символами).
- **Автодополнение кода** — `insert.js`. Остаётся коротким контекстом у курсора и использует `GET /api/variants`; оно должно заменять текущий токен/выделение, а не интерпретировать весь документ как задачу.

Это два контекста одного продукта, а не две отдельные классификации.

### Единый endpoint задачи

`GET /api/search/task?q=...` объединяет три источника:

1. **Направленные фразы** — запрос сопоставляется с фразами обычного `synonyms.json`; результаты ведут к каноническим терминам и их языковым разделам.
2. **Полнотекстовая библиотека** — `lib/search.mjs` ищет фрагменты по названиям, описаниям, тегам, разделам и коду.
3. **Дерево вариантов** — `lib/variant-tree.mjs` возвращает конструкцию и структурные отношения из общего парсера.

`lib/search-core.mjs` объединяет фрагменты reciprocal-rank fusion. Независимые исходные score не сравниваются напрямую: учитываются позиции в каждой выдаче. Точное совпадение с названием библиотечного фрагмента получает дополнительный вес, чтобы точный пример не терялся за большим количеством слабых смысловых совпадений.

Каждый фрагмент сохраняет:
- источники совпадения;
- найденные целевые конструкции;
- раздел и язык;
- причину совпадения и позицию в каждой исходной выдаче.

### Контекстные ограничения

Сопоставитель `lib/query-phrase-match.mjs` общий для дерева и направленных фраз. Он нормализует регистр и `ё/е`, использует токены и русскую стемматизацию, различает точное, префиксное и частичное совпадение, сохраняет отрицания.

Для снижения ложных совпадений есть контекстные проверки:
- массив/список не подменяется раскрываемым блоком;
- ссылка не подменяется кнопкой;
- наведение не подменяется нажатием;
- внутренний отступ не смешивается с внешним;
- толщина шрифта не смешивается с размером;
- межбуквенный интервал не смешивается с межстрочным;
- сохранение места не смешивается с удалением элемента из потока;
- интерфейсные задачи не должны получать случайные Python, SQL, file-I/O и диагностические фрагменты.

Для явно интерфейсного запроса приоритет получают HTML, CSS, JavaScript и SVG. Python остаётся доступен, если в запросе явно указана серверная/Python-часть.

### Классификация и словари

Дерево использует общий `public/structure-rules.js` и типизированные группы отношений. Отдельные пользовательские конструкции и фразы из отдельного хранилища не включаются в обычный task search.

В ходе сценарного аудита дополнены штатные языковые словари:
- JavaScript: DOM-селекторы, `response.json()`, `textContent`, `classList.toggle`, асинхронные конструкции и другие используемые элементы;
- HTML: `aria-expanded`, `aria-controls`, `hidden`;
- направленные фразы добавлены только под проверяемые задачи: раскрываемые блоки, hover-заголовки, несколько источников данных и вывод в разные DOM-области.

## Проверочные сценарии

`tests/real-library-search-audit.test.mjs` проверяет шесть реальных задач:
1. кнопка, действие по нажатию и сообщение;
2. ссылка на другую страницу;
3. раскрываемый блок;
4. подсветка заголовка в шапке при наведении;
5. данные из нескольких источников и вывод в разные части страницы;
6. сворачивание боковой панели.

Проверяются не только непустые ответы, но и обязательные конструкции и отрицательные случаи: ссылка не превращается в кнопку, сворачивание панели — в `.reduce()`, кнопка — в игровой/клавиатурный ввод, hover — в несвязанные свойства, обычная загрузка данных — в метаданные DOM-узлов или worker-сообщения.

Другие тесты:
- `query-phrase-match.test.mjs` — совпадения, отрицание и смысловые контрасты;
- `query-phrase-shadow.test.mjs` — составной запрос и отсечение ложной свёртки массива;
- `search-core.test.mjs` — объединение источников, provenance, приоритет точного названия и языковой контекст;
- `variant-tree-structure-rules.test.mjs` — общий парсер и 14 типов структурных правил.

## Ограничения и следующие проверки

Это не полноценный семантический планировщик. Система не гарантирует, что для любой произвольной задачи автоматически соберёт законченный проект. Она ранжирует существующие конструкции и фрагменты, используя словарные фразы, контекстные фильтры и структурные правила. Слабые совпадения ещё нужно проверять на новых запросах.

Остаётся:
1. завершить CI после последних изменений фильтрации и ранжирования на Ubuntu и Windows;
2. просмотреть итоговые результаты шести сценариев после последних фильтров;
3. проверить в браузере раскрытие групп, вставку фрагментов, отмену устаревших запросов, IME и клавиатурную навигацию;
4. расширять словарь только по подтверждённым пробелам, а не массовым добавлением синонимов.

Непустая выдача сама по себе не считается успехом. Критерий — правильные основные конструкции, корректные отношения, релевантные фрагменты и отсутствие проверяемых ложных подмен.
