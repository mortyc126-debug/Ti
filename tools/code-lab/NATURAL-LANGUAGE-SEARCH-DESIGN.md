# Проектирование поиска по описанию задачи

Дата: 2026-11-07  
Ветка: `audit/fixes-2026-11-06`  
Статус: проект решения по результатам чтения текущей реализации; production-поиск не переключён.

## Задача

Человек описывает результат обычными словами, не зная названий HTML/CSS/JavaScript-конструкций. Лаборатория должна помочь определить, какие элементы языка нужны, как они соединяются и какой код получится. Результаты остаются в обычной классификации языков и их разделов. Внутренние механизмы интерпретации запроса не становятся пользовательскими категориями.

Примеры запросов:
- «сделать кнопку, которая выполняет действие по нажатию»;
- «добавить ссылку на другую страницу»;
- «сделать раскрывающийся блок»;
- «подсветить текст заголовка в шапке при наведении»;
- «получить данные из двух источников и вывести их в разных местах страницы»;
- «свернуть боковую панель, чтобы её можно было снова открыть».

## 1. Что уже есть и почему этого недостаточно

Сейчас существуют три разных поисковых пути:

1. **`/api/variants` → `buildVariants()`**. По смысловым фразам из `public/dict/synonyms.json` находит термины и строит дерево вариантов. Именно его вызывают оба интерфейса подсказок.
2. **`/api/search` → `lib/search.mjs`**. Отдельный полнотекстовый поиск по библиотеке: названия, описания, теги, разделы, пояснения и код; BM25-подобное ранжирование, синонимные группы, основы слов, префиксы и опечатки.
3. **`/api/search/shadow`**. Экспериментальный теневой поиск направленных фраз. Он сравнивает кандидатов с действующим поиском, но явно не меняет production `/api/search`. Источники включают импорт фраз из legacy-словаря и отдельное хранилище; это не основание сохранять отдельную пользовательскую категорию в интерфейсе.

Дополнительно есть отдельная страница `concepts.html` со своим поиском и CRUD. Она не является нужным интерфейсом для описания задачи и не должна определять архитектуру основного поиска. Наличие направленных фраз в теневом эксперименте не требует отдельного пользовательского раздела: поисковая формулировка должна вести прямо к реальным элементам языка в их штатных разделах.

### Разрывы в текущей реализации

- `buildVariants()` проверяет, что все слова запроса помещаются в одну поисковую фразу. Длинное описание, в котором действие, объект и условие распределены по разным фразам, теряется.
- Синонимная фраза используется одновременно как совпадение и подпись результата. Она не сообщает, какая часть запроса совпала и почему выбран конкретный термин.
- Один термин может иметь несколько значений. «Свернуть» может относиться к `.reduce()` или к раскрытию/сворачиванию интерфейса; выбор должен зависеть от слов «массив», «список», «блок», «панель», «раздел».
- В дереве `variant-tree.mjs` собственный regex-парсер структуры не совпадает с общим `StructureRules.parse()`. Он не понимает `не содержит`, `первым в`, `значения`, `связывает`, `читает`.
- `code-links.js` добавляет ещё один слой отношений (`когда`, `если`, `откуда`, `куда`, `результат`), частично выводя их эвристически из начала пояснения. Его нельзя считать заменой явных структурных правил.
- `insert.js` и `vtree.js` обращаются к одному endpoint, но по-разному формируют запрос: inline-контекст ограничен текущей строкой и короткой русской фразой; поле «что нужно сделать…» имеет отдельную задержку 250 мс. Это разные входы, а не единый поиск.
- `insert.js` намеренно не показывает подсказку, когда курсор стоит посреди токена. Это разумно для автодополнения идентификатора, но плохо для ввода описания задачи.
- Текущий результат дерева — до 8 корней, в основном термины и примеры. Он не обязан собирать завершённую цепочку HTML → CSS → JS → данные и не проверяет полноту решения.

## 2. Целевая схема поиска

Поиск должен состоять из последовательных, проверяемых этапов. Это один поисковый механизм с разными способами ввода, а не набор новых пользовательских классификаций.

### Этап A. Получить запрос без потери смысла

Поддержать два контекста ввода:

- **Описание задачи** — свободная фраза или несколько предложений. Сохранять весь текст, не обрезать до четырёх слов и не пытаться заменить всю фразу одним фрагментом кода.
- **Подсказка в редакторе** — текущий токен/выделение, язык файла, позиция курсора и ближайший контекст кода. Не превращать её автоматически в длинное описание задачи.

Оба режима используют общий движок поиска и общие результаты, но передают разные контекстные поля. В режиме описания поиск не должен зависеть от того, где стоит курсор внутри слова. В режиме кода сохраняется точная замена токена и текущая клавиатурная навигация.

Ввод должен учитывать IME, вставку, переносы строк, отмену устаревшего запроса и язык активного файла. Debounce — настройка интерфейса, не способ исправления слабого поиска.

### Этап B. Нормализовать, не уничтожая важные слова

- Нормализовать регистр, `ё/е`, пробелы и формы русских слов.
- Сохранять технические идентификаторы, дефисы, точки, двоеточия и синтаксические знаки.
- Не удалять отрицания и слова, меняющие смысл: «не скрывать место», «без перезагрузки», «только при наведении».
- Не считать все предлоги и глаголы бесполезными: «из двух источников», «в разные блоки», «после клика» несут структуру задачи.
- Не расширять запрос глобальной заменой слова на весь список синонимов, если контекст указывает на другое значение.

### Этап C. Выделить смысловые признаки запроса

Внутреннее представление запроса может содержать признаки, но не должно показываться как новая классификация. Извлекать:
- объект: кнопка, ссылка, заголовок, блок, боковая панель, список, данные;
- действие/результат: перейти, отправить, раскрыть, скрыть, подсветить, загрузить, объединить, вывести, обновить;
- условие/событие: клик, наведение, фокус, загрузка, изменение размера, изменение данных;
- источник: API, файл, форма, локальное хранилище, несколько URL;
- место назначения: элемент страницы, несколько областей DOM, таблица, список;
- ограничения: без перезагрузки, с сохранением места, доступно с клавиатуры, один/несколько источников;
- контекст: активный язык, текущий файл, соседние элементы кода.

Признаки могут быть неизвестными или неоднозначными. Не нужно притворяться, что парсер всегда понял запрос. Если развилка меняет решение, система показывает 2–3 осмысленных варианта или задаёт один короткий уточняющий вопрос.

### Этап D. Найти кандидатов несколькими независимыми способами

Кандидаты должны приходить из четырёх источников с указанием происхождения:

1. **Точное имя конструкции** — HTML-тег/атрибут, CSS-свойство/селектор/псевдокласс, JS-метод/событие/оператор.
2. **Направленная поисковая формулировка** — обычная фраза ведёт к одному или нескольким каноническим терминам. Это не объявляет фразу синонимом термина. Например, «раскрывающийся блок» может вести к `details`, а «свернуть массив в одно значение» — к `.reduce()`.
3. **Лексический поиск** — основы слов, точные части составных имён, синонимы и опечатки. Он помогает найти кандидатов, но не доказывает, что они решают задачу.
4. **Примеры библиотеки** — готовые фрагменты по названию, описанию, тегам и коду. Пример должен подтверждать применение, а не подменять справочник языка.

Каждое совпадение хранит причину: точный термин, фраза, поле библиотеки, синоним, контекст языка или связь. Нельзя скрывать слабый лексический матч под видом точного ответа.

### Этап E. Собрать связи между штатными разделами языков

Канонические элементы остаются в разделах HTML, CSS, JavaScript и других языков. Поиск связывает их типизированными рёбрами, не сливая языки:

- HTML создаёт элемент/атрибут и его семантику;
- CSS выбирает элемент/состояние и задаёт внешний вид;
- JavaScript реагирует на событие, получает/изменяет данные и управляет DOM;
- данные связываются с источниками и местами вывода.

Источники рёбер:
- `StructureRules.parse()`: синтаксическая вложенность, порядок, запреты, требования, обязательные/необязательные атрибуты, допустимые значения, шаблоны, явные межъязыковые связи;
- `code-links.js`: управляющие и потоковые отношения «когда/если/откуда/куда/результат»;
- существующие контракты и анализ библиотечных фрагментов;
- явно размеченные связи в данных, если они имеют понятный тип и проверяемую цель.

Синонимы, совпадение префикса и близость названий не создают ребро. Семейство имён CSS показывается как семейство, а не как синтаксическое продолжение.

### Этап F. Сформировать решение, а не россыпь терминов

Для описания задачи результат должен содержать:

1. Короткое понимание задачи и явно отмеченные предположения.
2. Минимальный путь решения: какие элементы HTML, CSS и JS нужны и как они связаны.
3. Штатные разделы языка с конкретными терминами и короткими русскими объяснениями.
4. Минимальный рабочий пример, затем расширенный вариант, если задача требует нескольких источников/состояний/обработки ошибок.
5. Важные альтернативы с условием выбора, а не неупорядоченный список.
6. Ограничения и проверку корректности: обязательные части, допустимые значения, порядок, доступность, тип данных, ошибки загрузки.
7. Примеры из библиотеки отдельно от канонического синтаксиса.

В редакторе кода результат остаётся компактным: точная конструкция, пояснение, варианты продолжения и ограничения рядом с курсором.

## 3. Примеры ожидаемого разбора

### Кнопка с действием

Запрос: «сделать кнопку, которая выполняет действие по нажатию».

- HTML: `button`, `type="button"` (чтобы случайно не отправлять форму).
- JS: событие `click`, `addEventListener`, функция-обработчик.
- Связь: обработчик назначен именно этой кнопке.
- CSS: только если запрошено оформление.
- Не предлагать `a` как эквивалент кнопки: ссылка навигирует, кнопка выполняет действие.

### Ссылка

Запрос: «сделать ссылку на другую страницу».

- HTML: `a`, `href`.
- При открытии новой вкладки — отдельно объяснить `target="_blank"` и `rel="noopener"`.
- Не добавлять JS-кнопку, если достаточно обычной навигационной ссылки.

### Раскрывающийся блок

Запрос: «сделать блок, который можно раскрыть и свернуть».

- Базовый вариант: HTML `details` + `summary`; показать, что `summary` — первый элемент внутри `details`.
- Альтернатива: `button` + JS-состояние + `aria-expanded` + `hidden`, если требуется нестандартное поведение.
- Не путать с `overflow: hidden`, которое только обрезает содержимое, и с `.reduce()`, которое сворачивает значения массива.

### Подсветка заголовка в шапке при наведении

Запрос: «подсветить текст заголовка в шапке при наведении».

- HTML: фактический заголовок `h1`–`h6` внутри `header`; `header` и заголовок — разные элементы.
- CSS: селектор вроде `header h1:hover`, псевдокласс `:hover`, визуальное свойство `color`, `background-color`, `text-decoration` или другое по выбранному эффекту.
- Для клавиатуры — при необходимости `:focus-visible` на интерактивной цели; не приписывать фокус заголовку автоматически.
- Не выдавать только `:hover`: это условие выбора, а не само оформление.

### Данные из нескольких источников в разные части страницы

Запрос: «получить данные из двух источников и показать их в разных местах».

- JS: `fetch`, `Promise.all` или последовательный запрос — выбор зависит от зависимости источников; `await`, проверка `response.ok`, `response.json()`.
- Данные: два ответа, структура объектов/массивов и поля, которые нужны странице.
- DOM: два целевых элемента, выбранных через `querySelector`/идентификаторы.
- Вывод: отрисовать соответствующие части данных в разные элементы, а не просто вернуть один объект.
- Состояния: загрузка, ошибка одного/обоих источников, пустой ответ; повторное обновление — если требуется.
- Не объявлять `fetch` достаточным решением: он только получает ответ, но не связывает данные с отображением.

## 4. Ранжирование

Не складывать все совпадения в один балл без объяснимых причин. Сначала применять жёсткие контекстные ограничения, затем ранжировать:

1. Точное имя/синтаксис в подходящем языке и контексте.
2. Точная направленная фраза, ведущая к каноническому термину.
3. Совпадение нескольких признаков задачи (объект + действие + условие).
4. Подтверждённая типизированная связь с уже найденным элементом.
5. Релевантный пример из библиотеки.
6. Лексическое совпадение, префикс и опечатка.

Наличие результата в библиотеке не должно быть обязательным условием, чтобы показать сам термин языка. И наоборот: фрагмент библиотеки без понятного совпадения с задачей не должен подниматься только из-за общего слова.

Каждый результат должен объяснять:
- что совпало;
- к какому штатному разделу и термину это относится;
- почему связан следующий элемент;
- является ли связь фактом из правила, выводом из контекста или поисковой гипотезой;
- что не найдено или осталось неоднозначным.

## 5. Как проверять качество

Для каждого сценария фиксировать:
- точные ожидаемые термины в top-5;
- полноту цепочки между языками;
- отсутствие ложных эквивалентов;
- правильное различение альтернатив;
- русское объяснение каждого английского/технического термина;
- объяснение происхождения совпадения и связи;
- наличие минимального вставляемого примера;
- сохранение качества старых коротких запросов.

Негативные проверки:
- «свернуть массив» не должно выдавать `details` как основной ответ;
- «свернуть блок» не должно выдавать `.reduce()`;
- «ссылка» не должна автоматически превращаться в обработчик клика;
- «кнопка» не должна подменять ссылку;
- «скрыть, сохранив место» не должно получать `display: none`;
- «навести на заголовок» не должно ограничиваться подсказкой для кнопки;
- запрос данных не должен заканчиваться на одном `fetch`, если пользователь просит вывести их на страницу.

Метрики:
- recall точных целей в top-5/top-10;
- precision top-5;
- полнота обязательных межъязыковых связей;
- число ложных эквивалентов;
- доля результатов с русским пояснением;
- доля связей с проверяемым происхождением;
- число запросов, где нужен уточняющий вопрос;
- регрессия на текущем тестовом наборе и реальных запросах.

## 6. Порядок реализации

1. Сначала зафиксировать end-to-end сценарии и текущую выдачу как baseline.
2. Подключить общий `StructureRules.parse()` к построению дерева; отдельно протестировать каждый тип отношения. Не менять содержимое правил на этом этапе.
3. Развести отображение типов связей в дереве и не выдавать семейства имён за синтаксис.
4. Свести оба интерфейса ввода к общему поисковому ядру, сохранив разные контексты: задача и токен в редакторе.
5. Построить разбор признаков задачи и ранжирование поверх существующих словаря, синонимов, связей и библиотеки.
6. Добавить сценарные HTTP-тесты полного решения и негативные тесты неоднозначностей.
7. Только после сравнения baseline включать новый поиск в основной интерфейс.

До завершения этих этапов не заменять production-поиск и не наращивать синонимы наугад.


## Реализация в ветке audit/fixes-2026-11-06

Первая рабочая версия общего ядра добавлена, но остаётся проверка выдачи на сценариях и корректировка ложных совпадений.

- `query-phrase-match.mjs` — общий сопоставитель фраз для дерева вариантов и направленного поиска. Использует нормализованные токены и русскую стемматизацию, различает точное, префиксное и частичное совпадение. Сохраняет отрицание и смысловые уточнения; есть защитные проверки для контрастов «внутри/снаружи», «текст/элементы», «наведение/нажатие», «размер/толщина», «массив/блок», «ссылка/кнопка» и других.
- `query-phrase-shadow.mjs` использует тот же сопоставитель; результат содержит совпавшие токены, тип и покрытие фразы.
- `search-core.mjs` объединяет направленные фразы и полнотекстовый поиск фрагментов через reciprocal-rank fusion. Шкалы исходных поисков не сравниваются напрямую. В каждом результате сохраняются источники и объяснения совпадения.
- `GET /api/search/task` — единый поиск по полному описанию задачи. Он объединяет направленные фразы из обычного словаря, полнотекстовую библиотеку и дерево конструкций со структурными отношениями.
- Поле описания задачи в `vtree.js` использует новый endpoint. Встроенное дополнение кода в `insert.js` остаётся отдельным контекстом короткого токена и использует `/api/variants`.
- Экспериментальные пользовательские фразы из отдельного хранилища не включаются в обычный task search. Нормальная классификация остаётся по языкам и разделам; отдельной категории пользовательских конструкций нет.
- Для явно интерфейсных запросов приоритет получают HTML, CSS, JavaScript и SVG. Python не отсекается, если пользователь прямо упоминает серверную или Python-задачу.

### Проверка реальными запросами

В `real-library-search-audit.test.mjs` добавлены сценарии кнопки, ссылки, раскрываемого блока, hover-заголовка, данных из нескольких источников и боковой панели. Отдельные unit-тесты проверяют слияние источников, происхождение результатов, отрицание и смысловые контрасты.

До прохождения всех сценариев и CI это не считается завершённой реализацией. Критерий приёмки — не просто непустая выдача, а правильные основные конструкции, отсутствие заведомо неверных подмен и понятное объяснение связей между HTML, CSS, JavaScript и фрагментами библиотеки.
