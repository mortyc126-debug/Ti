# План объединения 151 пары одинакового кода

Статус: подготовка манифеста; исходная библиотека не менялась.

## Результат подготовки

Манифест строится скриптом `scripts/build-duplicate-merge-manifest.mjs` из read-only отчёта `audit-library-report.json`. В нём для каждой пары сохранены оба паспорта, заметки, orphanNotes, URL, hash кода и предложенный канонический путь.

По отчёту от 2026-11-06:

- 151 пара, и во всех 151 парах код совпадает побайтно после нормализации отчёта (`rawHash` совпадает).
- В каждой паре ровно один ID без автоматически добавленного суффикса `-mv...`. Он предложен как канонический: так сохраняется более старый стабильный ID и путь.
- Второй ID записан в `legacyIds` как кандидат на перенаправление к каноническому ID. Это пока только таблица совместимости: сервер сейчас ищет фрагменты по точному ID и не реализует разрешение таких алиасов.
- Во всех 151 парах различаются `desc`, `tags`, `aliases`, `component`, `source` и `wordNotes`. Это не пары для удаления: объединять нужно оба паспорта.
- Манифест содержит 1 535 записей заметок с обеих сторон; после устранения только полностью идентичных записей остаётся 1 473.
- У 103 обычных заметок совпадают позиция и текст токена, но различается provenance (`source`); в одном случае дополнительно различается `kind`. Тексты пояснений в этих общих позициях совпадают. Значит, в большинстве таких случаев это не смысловой конфликт, а различие происхождения/старого формата. Поля нельзя молча перезаписывать.
- 70 concept-записей встречаются в паспортах этих пар. Их нужно хранить отдельно от обычных заметок к токенам.
- Для пар обнаружено 12 уникальных URL. Они остаются частью исходных данных; назначение каждой ссылки не выводится только из наличия URL.

## Правила манифеста

1. Предлагается канонический файл со стабильным ID без суффикса `-mv...`; это рекомендация, не автоматическое решение.
2. Код не переписывается: манифест допускает пару только при совпадении hash.
3. Описание-кандидат выбирается по большей длине, но обе версии остаются в `files`, а авторство не выводится из длины.
4. Теги и aliases объединяются как списки без повторов. `aliases` здесь — поисковые варианты названия фрагмента, а не алиасы ID.
5. `component` нельзя заменить целиком одним объектом: требуется объединить ключи и вручную разобрать вложенные конфликты.
6. Заметки сохраняются с исходным файлом и коллекцией (`wordNotes`/`orphanNotes`). `kind=concept` вынесен отдельно. Совпадения по позиции не означают, что можно терять provenance.
7. Старый ID нельзя добавлять в `aliases`: это смешает маршрутизацию ID с обычным поиском. Нужен отдельный resolver/redirect map, который пока не реализован.
8. Удаление старых файлов допустимо только после реализации совместимости ID, проверки всех ссылок на ID, резервной копии и тестового восстановления.

## Обнаруженные ограничения текущего приложения

- `library-store.mjs` выдаёт и ищет запись по точному ID (`byId.get(id)`). Resolver для старых ID не обнаружен.
- `wordNotes` и `orphanNotes` сериализуются в объект фрагмента; при сохранении `store.save()` собирает заметки заново по токенам. Это нужно учитывать при переносе.
- `kind=concept` не обрабатывается отдельным UI/серверным путём. `placeNotes()` пытается привязать такую запись как обычное пояснение к токену; при сохранении её `kind` может стать типом токена либо запись может уйти в `orphanNotes`. Поэтому 481 concept-запись в библиотеке нельзя мигрировать через обычное редактирование/сохранение.
- Модуль `lib/concept-model.mjs` и тесты валидатора существуют, но сервер `tools/code-lab-server.mjs` не импортирует модуль и не содержит `/api/concepts` маршрутов. UI также не показывает отдельную карточку пользовательских конструкций. Модель пока не подключена.
- `public/dict/synonyms.json` и `library/_synonyms.json` — разные механизмы. Не переносить их содержимое в новую модель автоматически.

## Следующий безопасный этап

1. Реализовать и протестировать resolver ID без изменения файлов библиотеки.
2. Добавить dry-run merge, который создаёт новый набор файлов в отдельной временной копии и проверяет сохранность каждого поля/заметки.
3. Отдельно сохранить `concept`-записи и provenance, не прогоняя их через обычную токенизацию заметок.
4. Сверить все ссылки на старые ID в задачах, рецептах, схемах и сохранённых пользовательских данных.
5. Только после успешного сравнения и теста восстановления — выполнять реальную миграцию на резервной копии.

Скрипт манифеста ничего не меняет в `library/`. CI публикует JSON-манифест вместе с исходным отчётом как artifact.
