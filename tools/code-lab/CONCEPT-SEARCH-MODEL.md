# Модель поиска по пользовательским понятиям и старым словарям

Статус: проектирование следующего этапа. Никаких миграций или изменений поисковой выдачи этот документ не включает.

## Почему текущей модели недостаточно

В `concept-model.mjs` сейчас есть:
- `name`, `aliases`, `forms`, `definition`, `tags`, `examples`;
- типизированные связи между понятиями;
- поиск по этим полям и расширение только через `equivalent`.

Но в старом `public/dict/synonyms.json` хранится не синонимия, а направленная связь «ключ словаря → пользовательская поисковая фраза». Фраза может относиться к нескольким ключам. Если перенести её в `aliases`, потеряется направление и появится ложное утверждение о равенстве понятий.

Старые группы `library/_synonyms.json` — третья сущность: группы расширения полнотекстового запроса. Их члены могут быть синонимами, формами, значениями, операциями, частями или тематически связанными терминами.

## Предлагаемая структура

Не складывать всё в массив aliases. Добавить отдельный верхнеуровневый массив `queryPhrases`:

```json
{
  "schemaVersion": 2,
  "concepts": [],
  "relations": [],
  "queryPhrases": [
    {
      "id": "query-...",
      "phrase": "значение по умолчанию",
      "targetConceptId": "concept-default",
      "language": "python",
      "scope": "dict",
      "origin": "import",
      "confidence": 0.8,
      "source": {
        "file": "public/dict/synonyms.json",
        "key": "dict.get(k, default)"
      },
      "note": "Фраза запроса, не синоним ключа"
    }
  ]
}
```

Поля:
- `phrase` — исходная формулировка пользователя; не нормализовать при хранении.
- `targetConceptId` — пользовательское понятие; либо `targetKey` — ключ старого словаря/поискового индекса. Указывается ровно одна цель. Один phrase может встречаться у разных целей: это намеренная неоднозначность.
- `language` — язык/платформа, если известны; пустое значение означает общий контекст.
- `scope` — область применения: раздел, тип данных, API или иная контекстная метка.
- `origin` — manual/import/inferred.
- `confidence` — степень уверенности; не использовать как вероятность релевантности без калибровки.
- `source` — происхождение записи (старый файл, ключ или индекс группы); нужно для аудита и обратного преобразования.
- `note` — пояснение, почему фраза ведёт к цели.

Связи между понятиями остаются отдельными записями `relations`. Для них в перспективе понадобятся `language` и `scope`, иначе одно написание вроде `float` нельзя безопасно развести между CSS и типами данных.

## Как должен работать поиск

Порядок приоритета:
1. точное название понятия;
2. точный alias;
3. точная форма записи с совпадением языка;
4. query-phrase с совпадением scope/language;
5. частичное совпадение и морфология;
6. related-связи — только по отдельному режиму/фильтру, не как синонимы.

Правила:
- `equivalent` может расширять обычный поиск, только если отношение не ограничено несовпадающим контекстом.
- `related`, `contains`, `depends`, `example`, `opposite` не должны автоматически расширять обычную выдачу.
- Если одна query-phrase указывает на несколько целей, вернуть несколько кандидатов с меткой «неоднозначная формулировка», не сливать цели.
- При известном языке/разделе ранжировать подходящий контекст выше; без контекста не скрывать неоднозначность.
- В объяснении результата показывать канал совпадения: название, alias, форма, поисковая фраза, эквивалент, связанное понятие.
- Поиск должен сохранять provenance, чтобы можно было понять, из какого legacy-источника пришло совпадение.

## Совместимость и миграция

1. Сначала реализовать чтение v1 и v2: v1 при загрузке получает пустой `queryPhrases`; v2 проходит строгую валидацию.
2. UI обязан сохранять неизвестные/новые верхнеуровневые поля. Сейчас `concepts.js` собирает объект сохранения вручную, поэтому без изменения UI новая коллекция будет потеряна.
3. Сначала добавить API/модель и тесты без импорта старых словарей.
4. Подготовить dry-run импорта `public/dict/synonyms.json`: каждая запись остаётся направленной «phrase → исходный key», включая дубликаты фраз у разных ключей. Никакого автоматического переноса в aliases.
5. Для legacy-групп построить отдельный manifest с отношениями и контекстом. Не превращать группы в полные клики эквивалентности.
6. Сверить количество исходных записей, неоднозначность, round-trip и контрольную выдачу. Только после этого включать новый индекс параллельно.
7. Старые файлы остаются неизменными до отдельного решения о переключении и наличии отката.

## Обязательные проверки

- v1 файл загружается и сохраняется без потери данных;
- v2 queryPhrases сохраняются при редактировании любого понятия через UI;
- одинаковая фраза у двух целей не вызывает ошибку и не сливает цели;
- повтор одной и той же записи с одинаковым target/context выявляется;
- пустая фраза, отсутствующий target, неизвестный origin и некорректная confidence отклоняются;
- импорт сохраняет source key, phrase, язык и количество строк;
- контекст CSS не смешивается с Python/JS для `float`; контекст финансов не смешивается с объявлением `var`;
- старый /api/search продолжает выдавать те же результаты, пока новый индекс работает в shadow-режиме.

## Граница текущей работы

Это схема следующего этапа, а не команда немедленно повышать версию схемы. Перед реализацией нужно проверить все места, где хранилище понятий читается, сохраняется, экспортируется, восстанавливается или отображается. Изменение схемы должно быть обратно совместимым и не затрагивать библиотеку фрагментов.
