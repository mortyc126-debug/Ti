# Модель пользовательских конструкций Code Lab

Статус: проект решения, без изменения формата действующих паспортов и без миграции данных.

## 1. Что должна представлять конструкция

Пользователь может выделить слово, фразу или участок кода и сохранить его как самостоятельное понятие. Конструкция не обязана быть термином языка: это может быть пользовательское название приёма, последовательности действий, шаблона, правила или комбинации нескольких элементов.

У конструкции есть:
- устойчивый внутренний ID;
- основное название;
- краткое значение/объяснение;
- варианты названия (синонимичные формулировки);
- варианты записи (другой синтаксис, сокращение, альтернативная форма);
- область применимости: язык, среда, раздел и теги;
- примеры из библиотеки и ссылки на конкретные места кода;
- связи с другими конструкциями, каждая со своим типом.

Название, значение, варианты и связи редактируются независимо. Удаление варианта не удаляет само понятие; удаление понятия не должно автоматически удалять примеры и другие понятия.

## 2. Не смешивать разные виды совпадений

| Вид | Смысл | Влияет на обычный поиск |
|---|---|---|
| Основное название | Каноническое имя понятия | Да, точное совпадение — максимальный приоритет |
| Вариант названия | Другая формулировка того же понятия | Да, как эквивалент |
| Вариант записи | Альтернативный синтаксис/написание той же конструкции | Да, в подходящем языке/контексте |
| Связь | Другое, но относящееся к понятию понятие | Нет, только отдельный фильтр «связанные» |
| Пример | Фрагмент, где конструкция используется | Да, как результат-пример, но не как синоним |
| Составная конструкция | Пользовательское понятие из нескольких частей | Да, по собственному названию и описанию |

**Ключевое правило:** связь «событие → обработчик» не означает, что слова «событие» и «обработчик» — синонимы. Связи никогда не добавляются в поисковый словарь эквивалентов автоматически.

## 3. Предлагаемый формат хранения

Отдельный файл `library/_concepts.json`, а не перегрузка `.meta.json` фрагментов. Так понятие существует независимо от примера и может ссылаться на несколько фрагментов.

Структура верхнего уровня:
- `schemaVersion`: версия схемы;
- `concepts`: массив понятий;
- `relations`: массив типизированных связей.

Карточка понятия:
- `id`: постоянный ID, не зависит от названия;
- `name`: каноническое название;
- `definition`: смысл своими словами;
- `aliases[]`: варианты формулировок с типом `equivalent`;
- `forms[]`: варианты записи с полями `value`, `language`, `kind`, `note`;
- `scope`: языки/среда/разделы;
- `tags[]`;
- `examples[]`: `pieceId`, необязательные координаты/текст выделения и пояснение;
- `createdAt`, `updatedAt`, `origin` (manual/import).

Связь:
- `id`;
- `from`, `to`;
- `type` — стабильный ID отношения;
- `note` — необязательное уточнение;
- `origin` — manual/inferred/import;
- `confidence` — только для автоматически предложенной связи;
- `createdAt`.

Для связей используется существующий словарь `public/relations.js` как отправная точка, но хранится стабильный ID типа, не подпись на русском. Нужно отдельно уточнить направление у типов «пример для», «альтернатива», «дубликат» и не считать их потоком данных.

## 4. Типы связей

Первая версия должна включать:
- эквивалентность — только для понятий, которые действительно означают одно и то же;
- часть / состоит из;
- пример / пример для;
- требует / зависит от;
- вызывает;
- передаёт данные;
- возвращает;
- создаёт;
- преобразует;
- использует;
- предшествует / следует за;
- альтернатива;
- заменяет;
- конфликтует;
- обобщает / частный случай.

Эквивалентность лучше хранить как связь, но при построении поискового индекса включать в расширение запроса только явно подтверждённые эквивалентные варианты. Остальные отношения остаются графом.

## 5. Совместимость с текущими системами

Сейчас существуют две разные системы:
1. `public/dict/synonyms.json` — словарь терминов и формулировок, который также используется для автоподписей токенов. Его не следует превращать в базу пользовательских понятий.
2. `library/_synonyms.json` и `lib/default-synonyms.json` — группы расширения полнотекстового поиска. Сейчас некоторые группы объединяют смежные, но не тождественные слова. Это источник шумных результатов.

План совместимости:
- не удалять и не переписывать оба словаря при первом включении новой модели;
- пользовательские понятия хранить отдельно в `_concepts.json`;
- из старых поисковых групп переносить в `aliases` только подтверждённые эквиваленты;
- тематические/причинные/структурные группы переносить в `relations` с конкретным типом, если направление и смысл известны;
- сомнительные группы оставлять в legacy-файле и не расширять ими поиск по умолчанию;
- сделать отчёт миграции и возможность отката до переключения поиска.

## 6. Поиск

Порядок выдачи:
1. точное название и точная форма;
2. точный вариант названия;
3. совпадение по составным словам и словоформам;
4. подтверждённый эквивалент;
5. значение, теги и примеры;
6. связанные понятия — только если пользователь включил соответствующий режим, с явной подписью типа связи.

В результате показывать причину совпадения: «название», «вариант названия», «вариант записи», «значение», «пример», «связано: требует». Не смешивать причины в один непрозрачный рейтинг.

## 7. Интерфейс

Минимальный сценарий:
1. пользователь выделяет слово/фразу в редакторе или вставляет текст;
2. команда «Создать конструкцию» открывает компактную карточку;
3. поле названия заполняется выделенным текстом, пользователь может изменить его;
4. пользователь задаёт значение и при необходимости варианты названия/записи;
5. можно привязать пример к текущему фрагменту и добавить связь;
6. сохранение создаёт/обновляет понятие отдельно от паспорта фрагмента.

В карточке понятия должны быть отдельные блоки «Название», «Что означает», «Другие названия», «Варианты записи», «Примеры», «Связи». Нельзя использовать одно поле «синонимы» для всех этих сущностей.

## 8. Проверки и ограничения

- ID уникален; ссылки на понятия и примеры проверяются.
- Варианты названия нормализуются для поиска, но исходное написание сохраняется.
- Дубли вариантов внутри одного понятия запрещены; одинаковый вариант у разных понятий допускается только с явным предупреждением о неоднозначности.
- Циклы допустимы для некоторых отношений (например, эквивалентность), но для иерархии «часть/обобщает» нужны отдельные проверки.
- Автоматические предложения никогда не становятся подтверждёнными связями без принятия пользователем.
- Удаление/объединение понятия — транзакционное, с предварительным показом всех ссылок и резервной копией.
- Поиск по коду не должен менять код или паспорта.

## 9. Этапы реализации

1. Зафиксировать и протестировать JSON-схему и валидатор.
2. Добавить отдельное хранилище и атомарные операции CRUD.
3. Добавить API чтения/сохранения с проверкой ссылок.
4. Сделать интерфейс создания понятия из выделенного текста.
5. Добавить поиск по названию/вариантам/значению без расширения по обычным связям.
6. Добавить просмотр графа связей и фильтр «связанные понятия».
7. Подготовить миграцию legacy-групп с отчётом; переключать поиск только после проверки отчёта.

До завершения аудита и проверки совместимости действующие словари остаются источником старого поведения. Эта спецификация не разрешает автоматически переносить или удалять их содержимое.
