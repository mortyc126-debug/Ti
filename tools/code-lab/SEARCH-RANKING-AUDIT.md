# Аудит ранжирования и связей поиска задач

Дата: 2026-11-07  
Ветка: `audit/fixes-2026-11-06`  
Контрольный прогон исходной версии: GitHub Actions run `42347006108`, commit `13e2e2a204247b2ed3f43c3a809ffe26cd807dd9` (Ubuntu и Windows — success).

## Краткий вывод

Единый endpoint работает и возвращает конструкции из словаря, фразы и библиотечные фрагменты. Но успешный HTTP-ответ и наличие обязательных терминов ещё не означают качественную выдачу. На шести сценариях обнаружены систематические проблемы:

1. Корни дерева вариантов и направленные цели ранжируются независимо. Поэтому наиболее важный объект задачи может оказаться ниже вспомогательных состояний и свойств.
2. Частичное совпадение по одному слову даёт слишком много кандидатов. Общие слова «блок», «элемент», «текст» подтягивают несвязанные CSS-свойства и JS-конструкции.
3. Полнотекстовые фрагменты остаются в выдаче даже при слабой связи с найденными целями.
4. UI показывал название, раздел и источник фрагмента, но не описание и не связь с конструкцией, по которой он был найден.
5. Тесты проверяли наличие ожидаемых элементов, но почти не ограничивали позицию, число ложных кандидатов и качество связи.

## Причины в коде

- `query-phrase-match.mjs` допускает частичное совпадение, когда совпала половина короткой фразы. Это полезно для длинного запроса, но общие слова дают чрезмерное число кандидатов.
- `variant-tree.mjs` сортирует корни по собственному баллу совпадения синонимов. Результаты направленного поиска не влияют на порядок корней.
- `search-core.mjs` объединяет позиции направленного и полнотекстового поиска через RRF. Это объединяет источники, но не проверяет, насколько библиотечный фрагмент связан с найденной целью.
- Интерфейс `vtree.js` раньше не показывал описание фрагмента и список конструкций, с которыми он сопоставлен.

## Уже внесённые изменения

- Язык активного файла используется как мягкий коэффициент ранжирования (×1,12), а не как фильтр, отсекающий другие языки. Добавлены тесты на сохранение межъязыковой выдачи и на алиас `javascript → js`.
- Если upstream прислал пустой `matchedTargets`, но известен `targetKey`, связь с этой целью не теряется.
- В выдаче фрагментов показываются описание, источник совпадения, конструкции-цели и причина контекстного приоритета.
- Добавлена диагностика реальных сценариев: позиции и баллы целей/корней, совпавшие фразы, позиции фрагментов и их связи.

## Следующий порядок исправлений

1. По диагностике измерить, какие корни получают завышенный балл из-за одного общего слова; не удалять полезные частичные совпадения без контрпримеров.
2. Согласовать ранжирование корней с направленными целями и точным объектом/действием запроса.
3. Ввести мягкую оценку связи библиотечного фрагмента с целями задачи; не терять точный самостоятельный фрагмент, если фразового соответствия нет.
4. Развести основной рабочий путь и необязательные альтернативы. Не выдавать `display`, `overflow` и `.reduce()` как равнозначные способы свернуть интерфейс.
5. Добавить проверки ранга, доли ложных результатов и связности решения на тех же реальных сценариях и на новых формулировках.
6. Только после этого расширять тестовый набор и оценивать устойчивость поиска на незнакомых задачах.

## Критерий готовности

Для каждой задачи первые результаты должны содержать основной объект и действие, затем необходимые связанные конструкции. Каждая связь должна быть объяснима: совпадение по фразе, структурное отношение из правил или библиотечный пример. Наличие ожидаемого термина где-то в первых 60 позициях не считается успешным результатом.


## Второй проход: точность и сохранение связей

После первого диагностического прогона внесены дополнительные исправления:

- Общие слова сами по себе больше не дают сильного совпадения. В частности, «блок» не должен подтягивать `grid`, `height`, `width`, `position` и `display` для задачи о раскрываемом блоке; «текст/страница» сами по себе не должны притягивать `innerText` к обычной ссылке.
- Добавлены контекстные исключения: раскрываемый блок всё ещё находит `details`/`summary`, а «итог внизу» — `footer`.
- Для простой кнопки не выдаются `disabled` и `event.target`, если пользователь не просил отключение кнопки или определение целевого элемента события. Для hover-задачи не предлагается `textContent` как способ подсветки.
- Для обычной HTML-ссылки отсечены файловые символические ссылки.
- Из синонимов `response.json()` убрана неоднозначная фраза «получить данные»: получение данных должно находить `fetch` раньше, чем разбор JSON-ответа.
- Все направленные цели, не попавшие в ограниченный список корней дерева, добавляются в соответствующий языковой раздел. Это сохраняет `Promise.all`, `fetch`, `querySelector` и другие найденные элементы, даже если они не вошли в первые корни дерева.
- У фрагмента отображаются описание, источники совпадения и список целей, к которым он привязан. Язык цели определяется по лучшему корню, а не по случайному языку примера.
- Языковые алиасы нормализуются (`javascript → js`), а фильтрация по языку выполняется до ограничения числа результатов.
- Если агрегированный список направленных фрагментов неполон, связи и фрагменты восстанавливаются из целей. При этом основной ранжированный список сохраняет собственный порядок; резервная сборка ограничена лимитом и не должна путать позицию записи в библиотеке с поисковым рангом.

### Дополнительные проверки

Добавлены проверки на:
- подавление совпадений только по общим словам;
- порядок `fetch` перед `response.json()` для запроса нескольких источников;
- отсутствие ложных CSS/JS-целей в задачах кнопки, ссылки, раскрываемого блока и hover;
- наличие связанных фрагментов для `fetch`;
- восстановление целей и связей, когда `rankedPieces` пуст;
- сохранение всех целей у общего фрагмента и лучшего ранга;
- языковые алиасы и фильтрацию до лимита;
- сохранение языка CSS-цели при наличии JS-примера.

Примечание: полный прогон после последнего изменения проверяется отдельно на Ubuntu и Windows. Ранее прошедшие прогоны относятся к конкретным предыдущим коммитам; они не заменяют проверку текущего HEAD.


## Область поиска до ранжирования

Дополнительно обнаружено, что глобальный теневой индекс мог отдавать первые позиции Python-кандидатам (`get`, `list`, `sum`) даже для задачи сборки веб-страницы. Последующее отсечение Python оставляло пустой список направленных фрагментов, хотя в отдельных целях были связанные HTML/JS-фрагменты.

Исправлено:
- единая функция `inferTaskScope` используется и поисковым ядром, и серверным маршрутом;
- для задачи с явными элементами страницы сервер передаёт теневому поиску область `web` ещё до построения рейтинга;
- теневой индекс ограничивает связанные фрагменты по их фактическому языку: HTML, CSS, JS, TS и SVG. Секция словаря не используется как язык, потому что базовые JS-термины могут находиться в общей секции;
- языковые алиасы нормализуются до сопоставления;
- фильтрация области выполняется до лимита кандидатов, поэтому Python-кандидаты не вытесняют веб-конструкции из первых позиций.

Для задач с явным Python/серверным контекстом область `web` не навязывается. В сценарии нескольких источников дополнительно отсеиваются POST-запросы, авторизация, декодирование изображений, HTML-вставка, атрибуты и тестовые заглушки, если пользователь не просил эти подзадачи.


## Разделение похожих HTML/CSS-задач

Дополнительно уточнены реальные сценарии:
- Обычная кнопка не смешивается с формой и `submit`; форма появляется, если пользователь описывает отправку или поля.
- Переход на другую страницу ведёт к `a`/`href`, а не к ресурсному `link`; CSS-состояния ссылки, подчёркивание, image map и отмена стандартного действия не подмешиваются без соответствующего запроса.
- Раскрываемый блок не смешивается с группами сообщений и файловыми путями.
- CSS-псевдоклассы и at-rules классифицируются по синтаксису как CSS даже при наличии одноимённой записи в общем словаре.
- Для нескольких источников отбираются операции чтения, параллельного ожидания и вывода; POST, авторизация, декодирование изображений, HTML-вставка и тестовые заглушки не подмешиваются без запроса на эти действия.

Результат выдачи проверяется не только по наличию ключевых слов: тесты проверяют правильный язык, порядок целей, связанные фрагменты и отсутствие типичных ложных совпадений.


Отдельно исправлена причина неверной классификации `:hover`: часть псевдоклассов находится только в общем словаре, а не в `langs.css`. Поиск дерева распознаёт синтаксис `:`/`@` как CSS и допускает общий словарь как источник термина. Если у цели нет отдельного корня дерева, она всё равно попадает в направленные цели под CSS, а не создаёт ложный JS-корень.
