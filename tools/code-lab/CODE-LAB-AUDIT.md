2. **Встроенная ревизия словаря в приложении.** Это узкая эвристическая проверка нескольких категорий записей, а не полный аудит библиотеки.

Полный аудит содержимого Code Lab (дубли, поля, разделы, связи, паспорта фрагментов) ещё не выполнен. Это отдельная задача A13.

## Найденный файл «АУДИТ ПОКРЫТИЯ»

В библиотеке есть `library/json/АУДИТ_ПОКРЫТИЯ.json`. Это реальный отчёт, но его предмет намного уже общего аудита Code Lab. По содержимому он фиксирует проверку Python-библиотеки:
- 197 базовых + 38 добавленных фрагментов = 235;
- AST проверен у 235 файлов;
- парные метаданные проверены у 235;
- для новых скриптов записаны результаты запуска;
- `errors` пуст;
- исправлены 12 повторяющихся ID.

Это полезный отчёт о покрытии и технической целостности Python-фрагментов на момент его создания. Он **не** проверяет смысловые дубли, качество названий и описаний, поиск, словари, синонимы, HTML/CSS/JS или все пользовательские данные.

Дополнительно обнаружено, что его паспорт `.meta.json` имеет пустое описание и статус `needs_description`. То есть сам отчёт существует как файл библиотеки, но пока плохо представлен в пользовательском каталоге.

## Что делает встроенный аудит сейчас

### `POST /api/dict/audit`

Маршрут read-only. Проверяет:
- ключи на русском языке в базовом словаре и словарях языков;
- значения, похожие на списки синонимов;
- фрагменты библиотеки, которые эвристически выглядят как обычная русская проза.

Он не проверяет полноценно:
- смысловые дубли и одинаковые понятия с разными названиями;
- правильность раздела и подраздела каждого фрагмента;
- корректность всех паспортов `.meta.json`;
- отношения между словами, вариантами и конструкциями;
- пустые/противоречивые определения и неполные примеры;
- соответствие фрагмента заявленному назначению.

Это полезная точечная диагностика, но её результат нельзя считать полным аудитом.

### `POST /api/dict/clean`

Маршрут с `apply: true` удаляет ключи, у которых не сбалансированы круглые, квадратные или фигурные скобки. Это не смысловая проверка. Она может принять за мусор корректное имя/выражение и не заметить множество других видов испорченных записей.

**Не запускать массовую очистку с применением.** Сначала нужен read-only отчёт с исходными значениями и предлагаемыми действиями.

## Проверка восстановления после аварии

В рабочей ветке `audit/fixes-2026-11-06` добавлен crash-recovery протокол для двух маршрутов:
- `POST /api/library/restore`;
- `POST /api/backup/restore`.

Что делает новая реализация:
- до первой записи атомарно публикует журнал со всеми перезаписями, удалениями и новыми файлами;
- сохраняет резервные копии существовавших файлов;
- после полного применения атомарно создаёт маркер `COMMITTED`;
- при старте сервера до `store.init()`, миграций и `listen()` ищет незавершённые транзакции и откатывает их;
- откат идемпотентен: если процесс снова упадёт во время восстановления, следующий запуск повторит его;
- ограничивает пути журнала разрешёнными хранилищами и проверяет symlink;
- сериализует два restore-запроса и блокирует остальные API-запросы на время восстановления;
- если обычный откат завершился с ошибками, API блокируется до перезапуска, чтобы приложение не продолжало работу с потенциально смешанными данными.

Добавлены дочерние process-crash тесты: авария после первой записи, после всех изменений до commit-маркера и проверка, что уже зафиксированная транзакция не откатывается. CI расширен на Linux и Windows.

**Статус проверки:** изменения закоммичены, но результат GitHub Actions для push-запуска пока не подтверждён доступным статусом. Не считать CI зелёным, пока не появится завершённый успешный run.

### Границы защиты

- Протокол защищает от аварийного завершения Node.js-процесса во время этих двух restore-операций.
- Он не превращает все операции записи приложения в транзакции. Обычное редактирование, удаление, импорт словаря и прочие маршруты требуют отдельного аудита.
- Журнал и резервные копии находятся на том же диске: это не защита от физической потери диска.
- Полная гарантия при внезапном отключении питания не заявляется: принудительный `fsync` файлов и каталогов пока не добавлен.
- Старые манифесты восстановления, созданные до появления crash-журнала, не содержат достаточного состояния для надёжного автоматического определения незавершённой операции.
