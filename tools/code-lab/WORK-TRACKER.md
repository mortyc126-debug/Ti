# Code Lab — план работ и журнал выполнения

Статус: спецификация и поэтапная реализация; crash recovery для двух restore-маршрутов проверен CI на Linux и Windows.  
Основной документ: WORKFLOW-SPEC.md

## Правила
- Работать в ветке code-lab/workflow-spec или в отдельной рабочей ветке от неё.
- Не коммитить прямо в main.
- Перед изменением кода проверить актуальную ветку и открыть основной документ.
- Не выполнять массовую перезапись/миграцию пользовательских данных без журнала операций, снимка и теста отката.
- После каждой задачи записывать: что изменено, какие файлы, тесты, commit SHA, ограничения.
- «Готово» означает проверенное тестами поведение; код без теста не считается готовым.

## Параллельные задачи для других чатов/исполнителей

### Исполнитель 1 — инвентаризация записи
Цель: найти все места, где Code Lab создаёт, обновляет, удаляет или перемещает данные.  
Ограничение: только анализ, без изменения кода.  
Результат: таблица «действие → UI → API → функции → затронутые хранилища → побочные эффекты → текущая защита → тесты».  
Проверить сервер и клиентские вызовы: архивы, словари, задачи, рецепты, flows, data, workspace и Git Sync.  
Приёмка: нет необъяснённых записывающих маршрутов; для каждого указаны все затрагиваемые сущности.

### Исполнитель 2 — технический дизайн журнала операций
Цель: предложить дизайн журнала, снимков и безопасного отката для файлового Node.js-приложения без внешней БД.  
Ограничение: не менять код; Git Sync не считать решением.  
Результат: документ с форматом журнала, размещением snapshots, атомарным протоколом, crash recovery, конфликтами ручных правок, блокировками, тест-планом и оценкой места.  
Приёмка: разобран сценарий сбоя на каждом шаге и определён путь восстановления.

### Исполнитель 3 — аудит пользовательских маршрутов
Цель: сопоставить обещания интерфейса с реальным API и форматом результата.  
Ограничение: только анализ, без изменения кода.  
Результат: таблица «намерение → начало → ввод/копирование → обработчик → место хранения → побочные изменения → продолжение/отмена».  
Приёмка: каждый сценарий имеет однозначный маршрут или пометку «сломано/неполно».

### Исполнитель 4 — тестовая стратегия
Цель: спроектировать тесты пакетного импорта, обновления метаданных, восстановления архива, рецептов, словарей, миграций и rollback.  
Ограничение: не менять код.  
Результат: матрица тестов с фикстурами, ожидаемыми изменениями и негативными сценариями.  
Приёмка: тесты проверяют не только успешную запись, но и сохранность исходных данных при сбое и откате.

## Передача результата из другого чата

Попросить исполнителя:
1. работать от актуальной ветки/коммита, указанных в документе;
2. не менять main;
3. вернуть документ или изменения и SHA коммита;
4. перечислить, что реально проверено, а что предположено;
5. не отмечать задачу готовой без воспроизводимого теста;
6. не удалять и не перезаписывать пользовательские данные.
