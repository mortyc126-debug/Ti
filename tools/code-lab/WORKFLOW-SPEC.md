# Спецификация рабочих процессов Code Lab

Статус: проект спецификации, версия 0.1. Основание: аудит кода ветки main, состояние на 4 ноября 2026 года. Исходная точка аудита: commit 6059faf1b89d0848e3703d65b61c1551818ab49f. Документ описывает целевое поведение, а не уже реализованные функции.

## 1. Цель

Code Lab должен помогать выполнять операции с данными, а не заставлять пользователя знать внутреннее устройство приложения.

Пользователь выбирает результат («дополнить словарь», «добавить примеры Python», «собрать рецепт», «перенести проект»). Приложение само:
1. собирает необходимые исходные данные;
2. объясняет, что будет сделано и зачем;
3. готовит запрос и ожидаемый формат, если нужен внешний ИИ или файл;
4. принимает результат в том же рабочем процессе;
5. проверяет формат, полноту, связи и конфликты;
6. определяет добавления, изменения, удаления и пропуски;
7. автоматически создаёт контрольную точку;
8. применяет операцию;
9. показывает итог и предоставляет отмену всей операции.

Пользователь не должен помнить содержимое старых файлов, сравнивать архивы вручную, угадывать загрузчик или знать пути хранения.

## 2. Принципы

### 2.1. Одна задача — один маршрут
У каждого пользовательского намерения есть один вход, понятная последовательность шагов и однозначное место возврата результата. Если операция требует внешнего действия, интерфейс сохраняет контекст и возвращает пользователя в тот же процесс.

### 2.2. Формат скрыт за адаптером
Пользователь вставляет текст или выбирает файл. Система определяет подходящий формат и адаптер либо сообщает, чего не хватает. Пакетный формат нельзя молча трактовать как один обычный фрагмент.

### 2.3. Сначала смысловой анализ, затем запись
Предпросмотр сырого файла не является достаточной защитой. До записи система строит смысловой план по объектам и полям: что будет создано, обновлено, удалено, пропущено, объединено и какие зависимости затронуты.

### 2.4. Контрольная точка создаётся автоматически
Перед каждой изменяющей операцией автоматически сохраняется исходное состояние всех затрагиваемых объектов. Ручной экспорт пользователем не требуется.

### 2.5. Откат относится ко всей операции
Откат возвращает все затронутые объекты в состояние до операции, включая парные файлы и побочные изменения. Нельзя откатить только часть пакетного импорта.

### 2.6. История понятна человеку
Журнал показывает название операции, время, источник, результат, затронутые сущности в понятных терминах и доступность отката. Внутренние пути и JSON могут быть доступны в диагностике, но не являются основным интерфейсом.

### 2.7. Существующее содержимое не теряется
Никакая операция не должна незаметно удалять или перезаписывать существующие данные. Неоднозначный конфликт блокирует применение и требует безопасного решения.

## 3. Карта сущностей и источников истины

| Сущность | Назначение | Текущее хранилище | Источник истины |
|---|---|---|---|
| Фрагмент кода | Повторно используемый фрагмент | library/<язык>/<id>.<ext> и соседний .meta.json | Код — текст; метафайл — паспорт |
| Паспорт фрагмента | Название, описание, раздел, теги, пояснения, контракт | *.meta.json | Метафайл |
| Контракт фрагмента | Что фрагмент предоставляет и требует | component.provides/requires в метафайле | Сохранённый контракт; вычисляемый — подсказка |
| Рецепт | Именованный набор фрагментов | recipes/*.json | Файл рецепта |
| Схема конструктора | Граф блоков и связей | flows/*.json | Файл схемы; локальный undo браузера не заменяет серверную версию |
| Задача | Учебное/прикладное задание | Точное хранилище и формат требуют отдельной проверки | Уточнить при инвентаризации |
| Словарь терминов | Объяснения терминов | public/keyword-dict.json, public/dict/langs/* | Соответствующий файл словаря |
| Правило структуры | Ограничение синтаксической конструкции | public/dict/structure.json | Файл правил |
| Связь слов | Отношение между терминами | public/dict/relations.json | Файл ручных связей |
| Синонимы словаря | Поисковые варианты терминов | public/dict/synonyms.json | Файл словарных синонимов |
| Синонимы библиотеки | Поисковые синонимы фрагментов | library/_synonyms.json | Отдельный файл; не смешивать со словарём терминов |
| Примеры терминов | Привязки терминов к примерам | public/dict/examples.json | Файл примеров |
| Произвольный набор данных | JSON, не являющийся автоматически фрагментом или рецептом | data/*.json | Файл набора данных |
| Рабочий проект | Реальные файлы проекта | Выбранная пользователем папка; сведения в workspace.json | Файлы проекта |
| Очередь описаний | Состояние фоновой генерации | data/description-jobs.json | Служебный файл очереди |
| Журнал операций | История, снимки и откаты | Новая подсистема, ещё не реализована | Журнал и снимки |

### 3.1. Четыре разных типа отношений

| Тип | Что связывает | Смысл |
|---|---|---|
| Связи фрагментов | Один фрагмент с другим | Явная связь в графе |
| Связи слов | Термин с другим термином/категорией | Лексическая или смысловая связь |
| Правила структуры | Синтаксический элемент с ограничением | Где и как конструкция допустима |
| Контракты | Входы и выходы фрагмента | Что фрагмент предоставляет и требует |

В интерфейсе нельзя называть все четыре механизма просто «связями» без уточнения.

## 4. Каноническая модель операции

Любое действие, меняющее данные, проходит общий жизненный цикл:

1. Выбор намерения — пользователь выбирает задачу, а не API-маршрут или тип файла.
2. Подготовка — система собирает исходные данные, определяет зависимости и текущие версии.
3. Ввод — система показывает запрос/инструкцию и принимает текст или файл; контекст сохраняется.
4. Разбор — вход преобразуется в нормализованные сущности через подходящий адаптер.
5. Проверка — формат, обязательные поля, язык, разделы, ссылки, дубликаты, полнота и непротиворечивость.
6. Смысловой план — сравнение нормализованных сущностей с текущим состоянием.
7. Подтверждение — пользователь видит человеческое резюме последствий; опасные и неоднозначные действия не применяются автоматически.
8. Контрольная точка — до первой записи сохраняется исходное состояние всех затрагиваемых объектов.
9. Применение — все изменения выполняются как одна логическая транзакция.
10. Постпроверка — система перечитывает данные и проверяет инварианты.
11. Отчёт — создано/обновлено/пропущено, побочные эффекты и затронутые зависимости.
12. Откат — доступна отмена всей операции, если нет конфликтующих более поздних изменений.

### 4.1. Смысловой отчёт

Пример, числа условные:
- Добавлено: 4 фрагмента.
- Обновлено: 12 описаний.
- Изменены: 3 набора тегов.
- Пропущено: 2 дубликата без содержательных отличий.
- Не применено: 1 запись с неизвестным разделом.
- Побочные изменения: дополнены 6 терминов словаря.
- Контрольная точка создана; откат доступен.

Отчёт группирует изменения по сущностям и полям, а не только по числу изменённых файлов.

### 4.2. Правила сравнения

Сравнивать нормализованные объекты, а не только байты файлов:
- код — нормализовать переводы строк, не удалять значимые символы;
- метаданные — сравнивать по полям и учитывать источник поля (manual/imported/ai);
- теги и синонимы — сравнивать как множества там, где порядок не важен;
- рецепты и схемы — сравнивать по объектам, ID блоков и связям;
- словари — по ключам и значениям;
- связи — по типу, источнику и целевому объекту.

Изменение форматирования JSON не является содержательным изменением. ИИ не должен перезаписывать ручные поля без отдельного решения пользователя.

## 5. Архитектура контрольных точек и отката

Это новая подсистема. Текущие Git Sync, предпросмотр и локальный undo конструктора её не заменяют.

### 5.1. Запись журнала

Каждая изменяющая операция получает уникальный operationId и запись:
- id, type, title, createdAt, status;
- source: пользовательский ввод, файл/архив, ИИ-ответ или внутренняя операция;
- targetTypes: типы затронутых сущностей;
- changes: добавлено/обновлено/удалено/пропущено по объектам и полям;
- beforeSnapshot и afterSnapshot: ссылки на сохранённые версии;
- dependencies: связанные объекты и побочные изменения;
- rollbackStatus и rollbackOperationId;
- warnings, validation и error.

API-ключи и секреты в журнал не записывать.

### 5.2. Снимки
Снимок хранит точное исходное содержимое каждого затрагиваемого объекта, включая парные файлы фрагмента. Возможны копии содержимого или content-addressed blobs с контрольными суммами. Нельзя полагаться только на Git-коммит: Git Sync охватывает набор путей и не даёт транзакции конкретной пользовательской операции.

### 5.3. Атомарность и аварийное восстановление
- До изменения объектов снимок должен быть успешно создан.
- Применение использует staging/временную область и атомарную замену файлов там, где возможно.
- При сбое на середине операции все уже изменённые объекты возвращаются к снимку.
- Журнал помечается failed только после подтверждённого возврата исходного состояния.
- Если автоматический откат не удался, операция получает статус recovery_required; дальнейшие записи в затронутые объекты блокируются до восстановления.
- Нужно предусмотреть восстановление после аварийного завершения процесса между заменой файлов и записью статуса журнала.

### 5.4. Безопасный откат
Откат разрешён, если текущие версии объектов совпадают с версиями, созданными операцией, либо обратное изменение можно построить без потери данных. Если объект после операции изменён вручную, нельзя молча затирать его откатом: нужно показать конфликт и сохранить текущую версию отдельным снимком. Откат сам журналируется и не удаляет исходную запись истории.

### 5.5. Хранение
В первой версии не удалять историю и снимки автоматически. Позже добавить понятную настройку срока/лимита хранения. Перед очисткой показывать объём и последствия. Не удалять единственную копию, нужную для доступного отката.

## 6. Реестр рабочих процессов

### WF-01. Дополнение библиотеки пакетными фрагментами
Намерение: добавить или обновить набор фрагментов из ответа ИИ/текстового файла. Вход: формат с разделителями === Название | язык | раздел либо явно поддерживаемый архив.

Подтверждённый разрыв: интерфейс «пробелы → запрос для ИИ» формирует пакетный формат, но видимый общий загрузчик .txt отправляет текст в /api/import, где он может быть принят за один фрагмент. Серверный /api/ingest умеет разбирать пакет, но согласованный маршрут из этого сценария не найден.

Целевой маршрут: сформировать запрос → вставить ответ в то же окно → пакетный разбор → проверка каждого фрагмента → смысловой отчёт → снимок → импорт → отчёт и откат.

Критерии: несколько блоков создают несколько фрагментов; пакет не интерпретируется как один фрагмент; неизвестные разделы и пустые блоки отмечаются; обновление учитывает ручные метаданные.

### WF-02. Дополнение словаря терминов
Намерение: заполнить отсутствующие объяснения терминов. Система собирает пробелы, формирует точный формат, принимает ответ в том же сценарии, проверяет термины, строит смысловой отчёт, создаёт снимок и обновляет нужный словарь. Результат не направляется в загрузчик фрагментов. Нужно закрепить точные правила для языковых словарей.

### WF-03. Связи слов
Система собирает неклассифицированные термины, формирует запрос, принимает ответ в том же окне, проверяет допустимые категории и термины, сравнивает изменения, создаёт снимок и сохраняет ручные связи. Не смешивать со связями фрагментов, правилами структуры и контрактами.

### WF-04. Правила структуры
Система собирает термины без правил, формирует запрос, принимает ответ, проверяет категории из разрешённого словаря, сравнивает по терминам, создаёт снимок и применяет. Режим полной замены не должен удалять правила на основании неполного ответа: полнота набора проверяется отдельно, удаления показываются явно.

### WF-05. Создание и обновление рецепта
Текущий побочный эффект: пакетный импорт рецепта может одновременно создать недостающие фрагменты библиотеки и сохранить рецепт; неразрешённые позиции могут остаться без кода. Сохранение того же ID заменяет существующий файл.

Целевой маршрут: разобрать рецепт → разрешить ссылки → показать создаваемые/используемые/не найденные фрагменты → проверить порядок и полноту → единая контрольная точка для библиотеки и рецепта → применить → предложить «Открыть в Конструкторе».

### WF-06. Рецепт → Конструктор
На рецепте должна быть команда «Открыть в Конструкторе». Холст получает блоки, затем предлагает соединения по provides/requires, показывает основания и конфликты. Автосоединение отменяемо. Контракты помогают предложить связь, но сами связями не являются. Серверные версии схемы должны быть защищены журналом операций.

### WF-07. Задачи
Текущая сильная сторона: генератор учитывает существующие задачи; пакетный импорт разрешает ссылки и показывает неразрешённые. Риски: одиночный редактор сохраняет только первое задание из нескольких; повтор одного имени в пачке приводит к принципу «последний победил»; нет полного смыслового сравнения.

Целевой маршрут: запрос → пакетный ответ → разбор → поиск дублей внутри пачки и в хранилище → смысловое сравнение → снимок → применение. Одиночный редактор явно отклоняет многообъектный ввод и предлагает пакетный сценарий.

### WF-08. Импорт и восстановление архива
Текущий риск: фрагмент хранится парой файлов — код и паспорт; /api/library/restore пишет файлы напрямую, совпадающие имена могут перезаписать существующие. Экран «Данные» объединяет разные типы импорта и автоматически маршрутизирует содержимое.

Целевой маршрут: определить тип архива → проверить целостность и парность → сопоставить с текущими объектами → смысловой отчёт → снимки → применить как одну операцию → проверить результат. Неполный архив не считается полной резервной копией. Отсутствующий метафайл не должен приводить к удалению существующего паспорта. Произвольные JSON-данные не должны случайно трактоваться как библиотека.

### WF-09. Перенос из «Данных» в библиотеку
Текущий риск: действие импортирует фрагменты в библиотеку и одновременно удаляет исходные записи из data/. Это миграция, не обычный импорт.

Целевой маршрут: показать сопоставление исходных записей с будущими фрагментами → проверить дубли и неразрешённые записи → снимок источника и библиотеки → перенос → проверка → единый откат. По умолчанию исходные записи сохраняются; удаление источника — отдельный явный этап.

### WF-10. Генерация описаний
Очередь защищает поля с источником manual/imported и некоторые непустые поля без отметки источника. Целевой маршрут: выбрать фрагменты или «все без описания» → показать число объектов и разрешённые поля → снимок метаданных → очередь → проверка → отчёт. Код фрагментов этой операцией не меняется.

### WF-11. Синхронизация с Git
Git Sync — публикация/синхронизация, не контрольная точка. Он может охватить много папок и посторонние изменения. Не использовать Git Sync как единственный способ отката данных лаборатории.

### WF-12. Рабочая папка проекта
Рабочая папка содержит реальные файлы проекта; библиотека — повторно используемые фрагменты. Наличие функции/класса в проектном файле не создаёт автоматически объект библиотеки. Редактирование проекта и извлечение фрагментов — разные намерения. Массовые операции с проектными файлами используют общий журнал и снимки.


### WF-13. Пользовательские понятия и конструкции

Намерение: пользователь сам создаёт смысловые единицы из одного или нескольких слов и связывает их с вариантами формулировок и примерами кода. Это не просто список синонимов и не карточка фрагмента.

Целевая модель:
- Понятие — каноническое слово или термин с собственным определением.
- Конструкция — именованное выражение из одного или нескольких понятий/слов; пользователь может выделить слова в тексте или ввести выражение вручную.
- Значение — объяснение смысла конструкции простым языком, при необходимости с контекстом и примерами.
- Варианты — другие формулировки, словоформы, сокращения, англоязычные названия и технические идентификаторы. Вариант хранится отдельно от канонического названия, с указанием типа и языка.
- Связи — ссылки на составляющие понятия, родственные конструкции, языки программирования и подходящие фрагменты библиотеки.

Требования:
1. Пользователь может выделить одно слово или фразу и создать понятие/конструкцию без ручного редактирования JSON.
2. Одной конструкции можно назначить несколько вариантов, не превращая их в отдельные дублирующие записи.
3. У вариантов есть тип: синоним, разговорная формулировка, словоформа, сокращение, перевод или техническое имя.
4. Значение и варианты редактируются независимо; ручные данные не перезаписываются ИИ.
5. Конструкции могут состоять из нескольких слов и иметь вложенные связи с другими понятиями.
6. Конструкция может быть связана с одним или несколькими фрагментами кода, но не обязана иметь кодовый пример.
7. Поиск принимает обычную формулировку пользователя и ищет по каноническим названиям, значениям, вариантам и связанным понятиям.
8. Результат показывает, какое понятие/конструкция совпало и через какой вариант; поиск не должен молча подменять точное совпадение слабым.
9. Одинаковые варианты в разных контекстах не объединяются автоматически: например, одно слово может иметь разные значения в разных языках или областях.
10. Старые словари, synonyms.json и library/_synonyms.json сначала инвентаризируются; миграция выполняется только после сравнения и с возможностью отката.

Критерии приёмки:
- фразы из нескольких слов ищутся как единое понятие;
- запрос по любому сохранённому варианту находит каноническую запись;
- поиск различает одинаковые слова с разным контекстом;
- добавление/изменение конструкции не требует знания файлов и форматов;
- связанные фрагменты открываются из результата поиска;
- проверены точные запросы, словоформы, варианты, опечатки и запросы с лишними словами.

### WF-14. Аудит и очистка содержимого

Намерение: привести существующие словари, синонимы, паспорта фрагментов и разделы к непротиворечивой структуре, не потеряв полезные данные.

Целевой маршрут: read-only инвентаризация → классификация проблем → отчёт с примерами и точными источниками → план перемещений/объединений/исправлений → контрольная точка → применение небольшими пакетами → повторный аудит.

Проверять отдельно:
- точные и смысловые дубликаты;
- варианты, ошибочно записанные как самостоятельные понятия;
- фразы и определения, попавшие не в то поле;
- пустые, слишком общие и противоречивые значения;
- записи без раздела, языка или связанного примера, когда он ожидается;
- некорректные и устаревшие связи;
- фрагменты, которые являются текстовыми инструкциями, а не исполняемым кодом;
- расхождения между keyword-dict.json, dict/synonyms.json, словарями языков и library/_synonyms.json.

Никакое содержимое не удаляется только на основании эвристики. Сначала показываются исходная запись, предлагаемое действие и причина. Неоднозначные записи сохраняются до ручного решения.

## 7. Единый центр рабочих процессов

Нужен слой «Операции», который регистрирует сценарий, входной адаптер и ожидаемый формат, исходные сущности, проверки, план изменений, контрольную точку, применение, постпроверку, отчёт и откат.

Состояния операции: Подготовка → Ожидает результат → Проверка → Готово к применению → Выполняется → Завершено / Ошибка / Требует внимания.

Если вкладка закрыта после генерации запроса, операция должна оставаться доступной для продолжения. Нельзя полагаться только на состояние JavaScript в браузере.

## 8. Раздел «Данные»: целевое разделение

Вместо универсального загрузчика нужны отдельные действия:
- Импортировать фрагменты в библиотеку.
- Восстановить библиотеку из архива.
- Импортировать набор данных.
- Импортировать рецепты.
- Перенести записи в библиотеку.
- Экспортировать резервную копию.

Каждый сценарий выбирает свой адаптер, валидатор, список затрагиваемых сущностей и политику отката. Общая зона загрузки может определить тип файла, но не должна молча принимать решение с разрушающими последствиями.

## 9. Нефункциональные требования

- Локальный сервер остаётся привязанным к loopback; не ослаблять защиту Origin/Host.
- Не отправлять содержимое локальных файлов во внешние сервисы без явного действия пользователя.
- Не писать API-ключи в журнал и резервные копии.
- Импорт идемпотентен там, где возможно: повтор пакета не плодит дубликаты.
- Пакетные операции сообщают о частичном успехе; предпочтительно атомарное применение.
- Неизвестный формат, повреждённый архив и конфликт ID не должны молча пропускаться или перезаписываться.
- Ошибка проверки привязана к конкретной записи и объяснена понятным языком.
- Тестируются успех, конфликт, частичный сбой, откат и повторный запуск.
- Старые API можно временно сохранить как совместимые адаптеры, но пользовательские сценарии должны идти через единый слой операций.

## 10. Критерии готовности

Переделка завершена, когда:
1. У каждой пользовательской задачи есть один очевидный вход и понятный конец.
2. Результат ИИ/файла возвращается в тот же сценарий и разбирается правильным адаптером.
3. До применения пользователь видит смысловой список изменений.
4. Перед записью создаётся проверяемая контрольная точка.
5. Любую завершённую операцию можно отменить целиком, если нет конфликта более поздних правок.
6. Побочные эффекты явно показаны и входят в тот же откат.
7. Пакетный ввод никогда молча не становится одним объектом.
8. Миграция не удаляет источник без отдельного ясного действия.
9. Разные виды связей и словарей различимы.
10. Интерфейс не требует знания путей, расширений и API.
